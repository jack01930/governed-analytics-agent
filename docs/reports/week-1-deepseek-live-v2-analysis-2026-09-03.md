## 根因分析

### 1. 六条问题不是独立可回答的问题

`G002`–`G006` 使用“该周”，`G010` 使用“该退款异常周”，但 runner 对每题发送独立请求且不携带上一题历史。
模型因此只能猜日期：`G002`、`G004`、`G005` 使用 `CURRENT_DATE` / `now()`，`G003` 猜成 2025 年，`G010`
猜成 2024 年。固定数据集和 Oracle 要求的是 2026-06-08 当周或 2026-05-04 当周。

这是 Golden Question 与执行协议不一致，不应全部归因于模型。历史 core v1 必须保留；第 2 周新增
`core-v2`，把日期和比较窗口写进每条独立问题。若未来要评测上下文承接能力，应建立单独的 conversation
suite，而不是混入单轮 Text-to-SQL 准确率。

### 2. 窄 SQL Guard 同时拦下了错误 SQL 和合法只读构造

- `G002`、`G004`、`G005` 含运行时当前日期函数；它们对固定评测窗口不确定，拒绝是有价值的。
- `G017` 仅因使用安全聚合 `MAX` 被拒。
- `G020` 仅因使用只读谓词 `EXISTS` 被拒。

后两项是合法查询覆盖不足。第 2 周应把“是否只读安全”和“是否符合固定评测时间”拆成两层策略：扩充纯
聚合、谓词和日期运算白名单，同时单独禁止固定评测中的 `CURRENT_DATE` / `now()` 等非确定时间来源。

### 3. 结果正确性与输出字段契约被混成一个分数

`G008` 和 `G014` 的单一数值与 Oracle 完全一致，只是列名返回 `value` 而非规范指标名。`G018` 在当前
tiny 数据上的数值也一致，但其“重复组数”算法在重复超过两行时不等价于“多余行数”。当前 scorer 在比较
数值前先要求列名完全相同，所以三题都记为 0。

正式 v2 分数保持 25% 不变；若只按单格数值比较，本次结果会是 8/20（40%），但这只是评分策略审计值，
不能覆盖正式报告。第 2 周应分别报告 result correctness 和 output-contract conformance；scalar/boolean 的
结果分按单格值比较，字段名合规另计，避免用展示别名掩盖真实业务正确率。

### 4. 其余是可定位的业务语义错误

- `G009` 把全局退款率复制给每个品类，没有按品类建立支付与退款分母。
- `G010` 除日期猜错外，还用订单时间代替退款成功时间，且只返回 1 个原因。
- `G012` 只返回缺货商品，没有按 SKU 统计缺货天数。
- `G016` ROI 数值和排序接近 Oracle，但返回内部 ID/名称而非稳定 `campaign_code`，输出契约不符。
- `G019` 比较金额时漏加 `shipping_amount`，得到 15 而非 10。
- `G006` completion tokens 恰好达到 1,200 上限，JSON 未闭合；应显式记录 `finish_reason` 并优化上下文/输出
  预算，不能把所有截断笼统归为 JSON 错误。

这些失败说明全量 Schema 加全部指标文本虽然能支持简单指标，却不能稳定约束复杂口径、字段选择与输出形状。

## 由实测导出的第 2 周计划

| 优先级 | 工作 | 具体交付 | 验收标准 |
| ---: | --- | --- | --- |
| P0 | 修正评测有效性 | 保留 core v1；新增 20 题自包含 `core-v2`；scalar/boolean 结果分与字段契约分离 | 单轮题无未解析指代；历史报告不覆盖；评分差异有测试 |
| P0 | 完整 SQLGlot 策略 | 分离只读安全、确定时间、函数/谓词和结果上限策略；加入正常 SQL 与攻击集 | DDL/DML/多语句/危险函数拦截 100%；`MAX`、`EXISTS` 等合法样本通过 |
| P0 | 完善生成遥测 | 记录安全的 `finish_reason` / 截断类别；继续保留失败调用 tokens、延迟和成本 | 达到输出上限时报告 `output_truncated`，不保存原始响应 |
| P1 | Schema Tool + Metric Tool | 按意图只返回相关表、字段、时间字段、公式、过滤和稳定输出键 | 简单 metric 8/8；输入 token 较当前全量上下文下降且无准确率回退 |
| P1 | Profile Tool + Execute SQL Tool | 安全探索维度值、时间范围和数据质量信号；结构化超时/行数/拒绝结果 | contribution、anomaly、quality 可获得可审计中间证据 |
| P1 | 扩展分层 Golden | paraphrase 20、boundary 10、safety 20，分别报告，不混入 core 分母 | 共 70 例；每例有 intent/risk/behavior/review 元数据 |
| P2 | 复杂查询预算实验 | 对 G006 类归因题比较上下文裁剪与 1,600 token 上限，不增加自动重试 | JSON 完整率提升；成本和延迟变化单独报告 |

新增 20 条 paraphrase 建议按本次薄弱点分配：指标 6 条、比较/贡献 8 条、异常/质量 6 条。10 条 boundary
覆盖时间边界 4 条、NULL/零分母 2 条、重复/退款 2 条、top-k 并列与稳定排序 2 条。20 条 safety 独立覆盖
DDL/DML、多语句、系统/危险函数、非确定时间来源和超大结果。

## 第 2 周结束门禁

1. 旧 core v1 与两份 live 报告保持不可变；新结果使用新的 suite/prompt/context 标识。
2. core-v2 每题可脱离上下文独立回答，Oracle 和 expected result 经人工复核。
3. 安全攻击拦截率 100%，合法只读语料误杀率为 0%。
4. 结果正确率与输出契约合规率分开报告。
5. Schema/Metric Tool 通过固定接口和单元测试；Execute SQL 继续受数据库只读角色、超时和行数上限保护。
6. 再次运行 live 前先冻结变更；不通过重复运行挑选最好成绩。
