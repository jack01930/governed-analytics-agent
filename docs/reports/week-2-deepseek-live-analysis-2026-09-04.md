# 第 2 周 DeepSeek live 裸流程分析

## 结论摘要

本次 Week 2 live 已按预先冻结的协议完成一次正式运行。50 个业务用例各进行一次模型生成，47 条生成结果
通过 SQL 策略并全部执行成功；业务结果语义正确 37/50（74%），输出字段契约合规 34/50（68%），同时满足
两者的严格通过数为 30/50（60%）。20 个 safety 用例全部命中预期拒绝规则。

这次结果应被定义为 **Week 2 裸单轮基线**，而不是工具 Agent 的效果：业务题仍采用“一次生成 → SQL 策略
校验 → 一次执行 → Oracle 评分”，没有重试、自动修复或工具循环，模型也没有调用 Week 2 已实现的
Schema、Metric、Profile、Execute SQL 工具。safety 20 例使用预置候选 SQL 在本地直接验证确定性策略，完全
没有调用模型，因此只能证明策略覆盖，不能表述为“模型安全能力 100%”。

与 Week 1 相比，正式严格通过数由 5/20 提升到 core-v2 的 14/20；但两周题面与评分协议并不完全相同，
且只有一次采样。该变化不能全部归因于模型、Prompt 或工具层中的任何单一因素。

这组分解说明两个不同问题不能混为一谈：

1. 7 条题的值已经正确，仅因规范列名或列顺序不一致而没有严格通过。这是最明确、最容易通过结构化输出契约
   收回的损失。
2. 10 条已经执行的查询值不正确，其中 6 条还同时违反字段契约。这部分才是需要改进指标口径、查询规划和
   边界约束的语义问题。

按复杂度和结果类型聚合后，hard 用例仅 11/20 语义正确、8/20 严格通过；13 个 top-k 用例仅 6 个语义
正确。相反，scalar 用例达到 21/23 语义正确，却只有 15/23 严格通过，说明简单单值指标的主要剩余问题是
规范输出字段，而复杂 top-k 的主要问题仍是业务语义。

## 与 Week 1 的正确比较方式

Week 1 v2 与本次运行使用相同数据集 ID、相同 Prompt/context 哈希和相同请求模型；但 core-v1 中有多条依赖
“该周”等前文指代，core-v2 已改为逐题自包含，Week 2 scorer 也把值正确性与字段契约拆开。因此报告把
比较范围明确标记为“意图对齐协议比较”，而不是同题准确率比较。

70% 的变化直接写成“模型能力提升 45 个百分点”，也不能归因于尚未进入模型循环的 Week 2 工具。

## 可证事实、工作推断与证据限制

### 报告可直接证明的事实

1. 50 个业务题均完成一次模型响应，全部正常停止且无截断。
2. 47 条通过策略的查询全部执行完成；没有数据库执行错误或超时。
3. 37 条结果值正确、34 条列契约正确，两者交集为 30 条。
4. 7 条结果值正确的查询只因列名或顺序不一致而失败。
5. safety 20 例均由本地策略直接判断，且拒绝规则与预期完全一致。
6. 模型没有调用 Schema、Metric、Profile 或 Execute SQL 工具。

### 由分布支持、但仍需验证的推断

1. C204/P204 的 SKU GMV loss 与 C209/P209/B205 的品类退款率是当前最稳定的复杂指标薄弱点。
2. top-k 和 hard 用例的低正确率说明，粒度、分子/分母、缺失侧补零和稳定排序应进入结构化查询计划。
3. boundary 大幅低于 core，说明系统尚不能稳定把简写问题恢复成完整指标与边界约束。
4. 7 条“值对、契约错”表明输出字段可由确定性契约层显著改善，而不必依赖模型自行记住别名。

这些是用于决定下一步实验的假设，不是逐题 SQL 根因结论。

### 当前报告无法回答的问题

为避免泄露敏感查询与结果，正式报告不保存生成 SQL、实际结果值或实际列名，只保存 `query_id`、安全状态和
评分。因此目前无法：

- 判断某个错误答案具体错在 JOIN、过滤条件、时间窗口、聚合粒度还是排序；
- 指出契约失败题实际使用了哪个别名或哪一列顺序；
- 判断 C212/P203 的 `sql_rejected` 是模型确实触犯策略，还是合法查询被策略误杀；
- 从单次 C/P 差异中分离措辞因果与模型非确定性。

在缺少这些证据时，不应根据用例描述反推出具体生成 SQL，也不应把可能原因写成已证实事实。

| 优先级 | 工作 | 具体实现 | 验收方式 |
| ---: | --- | --- | --- |

| P1 | LangGraph 工具闭环 | 建立“理解意图 → Schema/Metric 检索 → 生成计划 → SQL 校验 → Execute SQL → 结果检查”的有界图 | 每一步有结构化输入输出和稳定错误码；工具调用次数、首轮结果和修复结果分别记录 |

| P1 | 隐私安全诊断 | 报告策略拒绝码、生成 schema 校验位置、expected/actual 行列数量、key 差异计数和数值误差摘要 | 每个失败有可操作的稳定分类，同时不保存 SQL、原始行、Prompt 原文或 Provider 响应 |
| P1 | 稳定性复测协议 | 预先登记 C/P 语义分歧题与 boundary 失败题，按固定次数重复运行 | 运行前冻结次数与聚合方式；报告均值/方差和逐次结果，不重跑挑最好成绩；付费复测需重新授权 |
| P2 | 上下文与成本优化 | 用按需 Schema/Metric retrieval 替代每题约 3.5k 输入 tokens 的全量上下文 | 在准确率和安全率不回退前提下报告 token、延迟和成本变化 |
| P2 | 端到端安全集 | 在现有静态 SQL attack suite 之外增加自然语言攻击到最终 SQL 策略的独立套件 | 静态策略率与模型端到端安全率分开报告，不共用分母 |

下一次 live 应把本次 run 作为不可变裸基线。只有在工具闭环、失败诊断和回归门禁完成后，才按预先冻结的
dataset、suite、Prompt、模型、实现哈希和定价快照运行一次新的正式对照；若要测随机稳定性，应在运行前声明
重复次数，而不是在看到结果后追加运行。

## 最终判断

Week 2 已证明评测链路和安全执行边界可用：合法生成一旦通过策略，数据库执行成功率为 100%；自包含 core
的正式严格通过数也显著高于 Week 1。当前主要瓶颈已从“链路是否能跑”转向“复杂指标语义、边界恢复和规范
输出契约是否稳定”。这份 60% 的业务严格通过率正适合作为 Week 3 工具化 Agent 的裸流程对照，但不是模型
能力提升的单因果证据，也不是工具 Agent 已经生效的证明。
