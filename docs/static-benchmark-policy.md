# 固定测试集与隔离评测规则

日期：2026-09-07。目的：建立独立于开发周次的共同测试标准。
状态：本文件定义规则；隔离的最终题库与执行环境尚未建立，不能将已有题库重新命名后视为独立测试集。

## 数据用途

| 集合 | 开发时能否查看 | 用途 |
| --- | --- | --- |
| 开发集 | 可以 | 提示词、代码、规则、工具和错误诊断 |
| 回归集 | 可以 | 检查已修问题是否再次出现，不作为未见问题成绩 |
| 最终测试集 | 实现与选型过程中不可查看题目、答案及逐题反馈 | 在实现冻结后比较预先登记的模型或系统版本 |

Week1、Week2 和现有 Week3 known/heldout 已用于开发或诊断，统一视为已见历史/回归材料。保留原文件、历史 cohort 字段和原始成绩；新报告必须标注其已见性质。

即使没有训练模型权重，查看测试失败后修改提示词、SQL 模板、规则、工具代码或选择模型，也会造成对测试集的适应。禁止把最终测试内容、参考 SQL、预期结果及逐题反馈加入 few-shot、RAG、项目记忆、微调数据或开发回归测试。

## 冻结与统一比较

1. 先固定支持范围、分类、分母和评分标准，再由与实现开发隔离的评测维护方编制、审核并封存题目与 Oracle。
2. 题面应有唯一可判定含义。等价改写、同源问题和答案模板按语义组检查交叉污染，不能仅按字符串去重。
3. manifest 必须绑定 benchmark 版本、题集哈希、数据库快照 ID、Oracle 哈希、评分代码版本，以及处理相对日期的固定参考时间。
4. 测试开始前登记所有候选及版本、配置、工具权限、预算、推理参数、重复次数和失败计分方式。历史运行不重新套用新分数；需要比较的历史实现应在共同协议下新增运行。
5. 比较模型能力时固定 Agent 框架、提示词和工具；比较系统版本时固定模型与外部条件，允许框架差异，但报告应称系统对照。不同能力范围按事先确定的子集分别计分。
6. 同一版本内，所有候选使用相同题目、数据、Oracle 与评分规则。基础设施失败单列并按预先登记规则处理，不选择性重跑失败题、不选最好的一次。

## 隔离边界

- 最终题库和答案不放在实现开发者或编程 Agent 可读的工作区；单纯 `.gitignore`、目录改名或换一个共享文件系统的会话不构成访问隔离。
- 被测模型在正式执行时必须看到当前题目，以及预先允许的 Schema、指标定义和工具结果；不得看到答案、参考 SQL、其他题目或评分器反馈。
- 各题使用独立会话与任务状态，禁止跨题记忆、测试成绩反馈驱动的适配，以及将测试轨迹自动写入案例库。
- 实现代码不得访问题库/Oracle 路径。评分在独立边界执行，原始逐题材料保留给评测维护方，开发侧正式报告默认只含总体/分类统计与运行身份。
- 服务商侧的数据留存和训练使用需要单独核实所选服务及账户策略；本地隔离不能保证服务商不留存或不使用数据。

## 发布与生命周期

- 一次发布对应一批提前冻结的候选；重复次数提前固定，报告全部运行、逐题配对的汇总差异、成本、延迟和不确定性。
- 固定题目可以重复用于受控比较，但根据测试结果反复调参会逐渐损害其独立性。记录每次提交与接触范围，限制将最终测试当作开发反馈循环。
- 如需开封错题进行诊断，该部分转为已见回归材料；此后的修复效果不能再以这些题宣称独立泛化。下一轮正式验收使用新封存版本，并披露版本差异。
- 题目或 Oracle 确有错误时追加版本与勘误，不覆盖历史，不删除难题抬分。不同测试集版本的百分比不能直接相减。

正式题目不在本开发会话中生成或阅读，以免由同一实现维护者同时接触测试题并继续调优。按 2026-09-07 的收尾安排，最终题库和统一评测延期到各候选完成后或求职前；届时先完成隔离题库、共同入口与候选登记，再进行统一测试。当前继续开发与回归验证；本规则文档不表示这些基础设施或测试已经完成。
